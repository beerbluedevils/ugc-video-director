# Workflow and scope

Use [execution.md](execution.md) for phase ownership, compact handoffs, download polling and the 300-second measured target.

## Completion and no-repeat rules

These rules apply to the existing steps below and their references. They do not create an additional review phase.

- Every new session uses the known button routes in browser.md and the phase procedure as its default path. Read required instructions once per phase; bind the next known action to current UI state. Complete evidence means advance immediately. Routine button selection and local bookkeeping require no agent question or coordinator approval.
- The coordinator owns invocation bookkeeping: capture a local dispatch timestamp, actual arguments and returned handle when invoking each required agent; persist these with the returned result. Pass available evidence in the handoff; agents must not pause browser/content work to request it. If no opaque ID or provider timestamp is exposed, record the returned task name and the limitation. Label local dispatch/recording times accurately. Missing provider telemetry is not a blocker when successful invocation and returned-result evidence exist.

- Perform each required check once at its specified step. As soon as its required evidence is complete, record it and proceed directly to the next authorized step. Do not reread the page, rerun the helper, reopen the file, repeat the search, or request a second agent review for reassurance.
- Use one supported UI observation method when it supplies the required evidence. Use another method only to obtain a specific missing field; do not require AX + DOM + screenshot for the same facts. A user-supplied screenshot can satisfy the visible fields; retrieve only any required field still missing, such as post ID/URL.
- Recheck only the affected facts when an actual action changed them, evidence conflicts, a required field is missing, or an applicable documented recovery requires it. Elapsed time, a model/agent handoff, unchanged post counts, or coordinator uncertainty alone do not invalidate evidence. Observe pending operations only until their documented success/failure evidence appears; then stop polling.
- The coordinator sends each required agent one complete phase assignment with paths, authorization and completion criteria. Browser phases are product preparation, then Flow through the authorized TikTok endpoint after the content handoff. Do not split these phases into coordinator approvals after every UI action. Do not repeatedly request status or ask the agent to repeat checks already reported complete. User status requests require a brief answer, not another verification cycle.
- A blocker requires the exact failed documented step and actual missing requirement or observed error. Do not invent eligibility rules, infer tool absence from one API surface, or ask the user to perform a step before completing its documented procedure/recovery. Do not create a new project merely to make selection easier unless the procedure or user request calls for it.
- Explicit ProductId/variant selection and automatic In Progress batch selection are different scopes. Do not reject an explicit selection solely because a shared listing ID appears in Done rows for other variants, or silently call it a new version. Apply the existing completed-job/duplicate rules to the actual selected variant and content; a confirmed completed matching job still requires an explicit new-version request.
- Keep the original requested endpoint. Sheet-write authorization is independent: when scheduling is verified and sheetWrite=false, record the unchanged sheet and finish the requested scheduling endpoint without requesting additional permission or treating the successful schedule as a failure. Retain the existing job stage vocabulary.
- Every next action below is conditional on the requested endpoint. Stop after Storyboard Ready for endpoint storyboard, Video Ready for video-ready, and the observed upload state for tiktok-upload. A table row or later numbered step does not authorize continuing past that endpoint.
- Record the stage result and its required evidence together in one job update, including current flags and summary. Preserve prior errors unchanged; add resolution notes separately. Run records contain pointers and aggregate outcomes, not copies of product metadata/forms. Do not perform extra UI actions to repair local JSON.

## Minimum evidence and mandatory advance

This section defines the sufficient completion threshold for each existing step. Collect these facts during execution, not in a separate review pass. When every required fact in a row is recorded, the agent MUST take the next authorized action immediately. Neither coordinator nor subagent may add another check, review, screenshot, approval question or waiting gate. For completion thresholds and whether to recheck, this table and the no-repeat rules govern all local phase references. The detailed references specify how to obtain these facts; repeated mentions describe the same observation, not an additional completion review. Higher-priority tool requirements and explicit user requirements still apply.

One observation can satisfy multiple facts. Tool-returned state, supported UI text/DOM, clipboard, an actual image observation or an existing recorded observation is sufficient for the facts it exposes. Do not require multiple observation methods for the same fact. Record source and local observation/recording time once; screenshots are optional unless they are needed to see a required visual fact. A handoff or new session alone does not invalidate recorded evidence.

Never repeat a generation/upload/Schedule request merely to obtain evidence.

## Daily quantity

- Resolve `videosPerDay` as a positive integer from the current request, otherwise `config.batch.defaultVideosPerDay` (3). Store it in the run with `videosPerDaySource` (`user` or `config`), `totalRequested` and authorized `dateScope` in Asia/Bangkok. Pass these fields in browser assignments. This setting does not change Flow outputs x1 or the required models.
- An explicit product list or total count bounds the work. Never add products to fill a daily quota. For “ทำวันนี้” or another single authorized day without a total/list, select at most videosPerDay eligible In Progress products. For an explicitly bounded date range without a total/list, select at most videosPerDay times the number of authorized days. A daily quantity alone without a date range authorizes one day's batch, not an indefinite run or recurring automation.
- For video-ready/storyboard/upload-only, the daily quantity bounds automatic batch selection; it does not authorize publication. Existing duplicate/skip rules remain and skipped products are not silently replaced. A request exceeding one day's capacity can proceed across days only when those dates are authorized; otherwise report the remaining count without moving it to another date.
- For scheduling, videosPerDay is the maximum total videos allocated to an account/date, including existing live scheduled/published posts and outstanding local reservations, deduplicated by post identity or matching job/content; do not count the same post in both places. Drafts do not consume a scheduled date. A retry or resume does not consume another video. Remaining capacity is max(0, videosPerDay minus the deduplicated count), also bounded by available authorized slots. Record this count and source evidence with scheduleReservation during the existing slot check, not a second preflight.
- Configured slots remain 11:00, 14:00 and 17:00. A smaller daily limit uses only the remaining allowed slots. A larger requested quantity does not invent times: use additional explicit user times if supplied and permitted by the actual form, otherwise report the slot shortage. Do not change configured slots, exceed the quantity, or shift a fixed date automatically.
- Daily quantity is a cap/selection default, not a guarantee of available products or slots. Retain sequential execution, authorization limits, duplicate checks and stop-batch failures. No extra approval is required for actions already within the resolved scope.

## Existing execution sequence

1. Interpret the request as explicit ProductId/PID selections or a bounded count of eligible In Progress rows. Resolve PID to exact ProductId using the current sheet; never use float IDs. Freeze the selected list in `runs/<RunId>.json`; do not silently add replacements for skipped items.
2. Record `workflowVersion`, request text, product list, endpoint and permissions in the run. Endpoints: `storyboard`, `video-ready`, `tiktok-upload`, `tiktok-scheduled`. Default to video-ready when publication scope is unspecified. For ambiguous upload versus posting, prepare safely and clarify before submission. Record sheet-write authorization independently; test-only jobs do not mutate Sheets or TikTok.
3. Read product job and verify current state/files. Skip completed items; resume incomplete work at the first unverified step. An ID already present does not make an unfinished item ineligible. Do not refill an existing ID.
4. Read product and variant facts; fetch/open real product image in temp; store source/variant/row in job. Mark Image Ready only after verifying it.
5. Apply Director v3 and image generation. Check storyboard and content. Store storyboard + TikTok caption, and embed both prompts in job; mark Storyboard Ready.
6. Generate with the Flow reference procedure; verify progress/failure/success. Retry only confirmed failure up to three times after initial generation. Persist results; do not reset on handoff. Exhaustion sets Generation Failed and stops the whole batch.
7. Download existing completed asset at 720p; inspect real file, image and audio as available; record unverified aspects. Mark Video Ready. Stop here unless further action is explicitly authorized.
8. For authorized TikTok upload, inspect duplicate posts/drafts and account, upload the verified file, insert exact caption, attach matching product. If only upload is authorized, do not Schedule/Publish; record draft state only if actually observed, otherwise record the unfinished form and handoff requirements.
9. For authorized scheduling, choose an unoccupied current/future allowed slot using live TikTok entries and reservations in all jobs/run records. Submit once and verify the actual Scheduled row, ID/URL and timezone. Persist Scheduled — Pending Sheet Update immediately.
10. If sheet update is authorized, verify row identity, update only its Status to Done and read back Saved to Drive; mark Completed and return TikTok Posts. Done means scheduling verified, not publication at the future time.
11. Summarize per-item outcomes and blockers in jobs; run record stores product pointers and aggregate counts, not copied product metadata. Stop at requested endpoint/count. No recurring automation unless requested.

Run fields: `videosPerDay`, `videosPerDaySource`, `totalRequested`, `dateScope`, `runId`, `workflowVersion`, `startedAt`, `updatedAt`, `request`, `productIds` (strings), `endpoint`, `permissions` (`sheetWrite`, `tiktokUpload`, `tiktokSchedule`), `failurePolicy: stop-batch`, `status`, `items` (productId/jobPath/outcome), `summary`. Write before side effects and after each item. The per-product job is authoritative; reconcile stale run summaries from jobs.

## Handoff contract

A phase assignment contains paths, exact product/variant, endpoint, persistent permissions, current verified stage, required procedure and completion criteria. The agent returns one phase result with artifact paths, observations, limitations and actual blockers. Intermediate messages are progress reports, not approval gates. Continue routine documented actions without waiting for replies. Ask only when required user intent/authorization is genuinely missing or an observed blocker has no documented recovery. The Image Ready → content → Storyboard Ready handoff remains required; it does not invalidate prior evidence. Resume sessions retain authorization and completed evidence; read only the missing or changed facts. Stop at the authorized endpoint.
